## 3. What Should Be Redesigned

### Architecture

| Component | Problem | Redesign |
|---|---|---|
| Command System | 107 stubs | Reduce to 20-30 with real handlers or map to actual capabilities |
| Workflows | In-memory, sequential, no retry | SQLAlchemy WorkflowRun + DAG `depends_on` support |
| Hermes security | `validate_action(**kwargs)` doesn't intercept anything | `@security_check` decorator wrapping ALL execution |
| Learning Engine | MetricEvent written, never consumed | Reactive pipeline: MetricEvent → Analyze → behavior change |
| COPILOT decisions | 100% static, no memory/KG consulted | `recall()` + `get_neighbors()` + RewardLearner before decisions |
| Financial Hub | 9 advisory modules, zero events | Publish events on KYC/route/tax changes. Connect to KG |
| Offensive pipeline | Ends at hypothesis, no findings | Add HTTP probe + Hypothesis→Finding + report render |

### 3 critical gaps summary

ORION has excellent architecture but 3 fatal gaps:

1. **No HTTP requests** → cannot confirm vulnerabilities. It's a hypothesis engine, not offensive intelligence.
2. **No rendered reports** → cannot submit findings to platforms. Pipeline ends before revenue.
3. **Learning is write-only** → 8 open feedback loops. System collects data but doesn't improve with use.

Closing these 3 gaps transforms ORION from a "suggestion assistant" to a "system that finds, validates, reports, and collects".
